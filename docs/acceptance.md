# 本地验收与审查流程

实现模型按功能规格写代码和测试。本聊天承担设计符合性审查，依据实际文件和本地执行结果更新 [执行计划](../EXECUTION_PLAN.md)。本文中的测试与命令是待实现目标，当前结果以执行计划为准。

## 1. 环境

基线为 Python 3.11+、Git 和本地虚拟环境。测试依赖选用 `pytest`，项目通过 `pyproject.toml` 声明包和开发依赖。实现者记录实际 Python、pytest、操作系统版本。模型运行器另配置本机模型。

安装依赖属于环境准备步骤，完成后测试可以断开外网。在本机 shell 遵循已有 RTK 指令，例如 `rtk proxy .venv/bin/python -m pytest ...`。IDE 的测试配置使用同一个 `.venv` 解释器与工作目录。

## 2. 每个功能的实际操作

1. 根据执行计划领取可用功能，在功能交接文件登记实施者和修改范围。先阅读[公共契约](contracts.md)、[跨功能接口矩阵](interfaces.md)和相关专项规格。
2. 完成代码、测试及必需的合成夹具。对共享契约的必要变化写出原因和影响功能。
3. 执行该功能的测试命令、依赖回归和语法检查。记录完整命令、开始时间、耗时、退出码、通过/失败/跳过数量以及日志位置。
4. 为被测试的实现、配置、提示词和测试文件生成相对路径及 SHA-256 清单，保存到 `local/verification/<feature>/<run>/tested-files.json`。实现源码、测试、夹具、配置或提示词发生变化后，重跑受影响检查并更新清单。
5. 在 `local/handoffs/Fxx.md` 中写明 `ready_for_review` 建议及交接记录。自测失败则记录 `in_progress`、失败和下一步。
6. 本聊天读取对应文件和日志，复跑功能测试，对照验收表检查关键条件，并统一更新执行计划。通过后标记 `accepted`，需修改时标记 `changes_requested` 并列明位置与原因。

自测通过和设计审查通过分开记录。模型回复“应当通过”、只有预期输出、IDE 无报错、语法编译成功，都不能填写测试 `passed`。

## 3. 通用本地命令

各功能规格给出准确的测试文件。以下命令在仓库根目录执行，代码实现后才具备运行条件。

```sh
.venv/bin/python -m compileall -q src/context_manager
.venv/bin/python -m pytest tests/test_f01_foundation.py -q
```

本机使用 RTK 时，在以上命令前加 `rtk proxy`。测试成功后保留原始输出和退出码，不能只保存筛选后的成功行。

测试利用临时目录构造项目。验证规则文件读取或补丁预览时，对目标仓库文件生成前后摘要并断言无变化。文件夹具应有相似名称、范围例外、重复事件和缺失回执等负例。

## 4. 语义 Agent 的测试

F06 分两类检查，每类实际结果单独记录。

| 检查 | 本地执行方法 | 通过意味着什么 |
| --- | --- | --- |
| 工具循环和边界 | 固定模型响应驱动真实运行器，覆盖坏 JSON、非法工具、越界读取、无引用、超预算、失败重试 | 运行器按约定处理输入和错误 |
| 本地模型语义案例 | 连接本机模型，实际运行固定案例集，每例运行 3 次，记录候选及裁定 | 当前模型配置在这些案例上的结果达到规格 |

本地模型案例至少覆盖等义改写、兼容例外、历史引用、未决需求、真假复发和日志提及。采用 F06 中明确的标签及证据门槛断言，并人工复核输出。自动断言检查类别、引用和越权行为，人工检查解释与删改是否遗漏有效约束。

本地模型不可用时，保留 `local_model_test: not_run`，F06 不能标为 `accepted`。先准备本地运行环境再完成该项，禁止把固定响应的结果替换为真实语义通过。预算只限制本地调用次数、耗时和返回内容量。

## 5. 审查记录必须回答的问题

- 入口能否在正常调用路径实际完成该功能，接口和枚举是否与契约一致。
- 关键正例是否达到预期，负例和材料缺失时是否得到正确结果。
- 测试是否会在功能被破坏后失败，是否绕开了正式实现或直接复制预期报告。
- 候选引用是否指向实际快照，报告是否保留来源、合成标记、失败和未执行项。
- 补丁是否保留独立义务和例外，是否超出规则文件和批准范围。
- 修改是否影响已通过功能，是否复跑相关回归。

审查在执行计划中写明 `accepted` 或 `changes_requested`，附对应文件和行号、实际命令、问题及修复后的复核结果。只有代码发生变化或存在新的未决问题时，才追加相应回归。

## 6. 最终统一交付

开发阶段可以按明确的发布指令提交已验收功能和后续检查计划。阶段快照的首页须标明已实现能力、待实现项与实际测试范围。完整工作流的发布按本节门槛完成，后续以远端实际分支为基线推进。

F01–F09 都达到 `accepted` 后，F10 运行整个基础测试集、本地模型案例、CLI 集成与打包检查。最终测试清单绑定全部实现和测试文件摘要。在准备提交后用暂存区与该清单对照，任何实现变更均使相关结果过期。

```sh
.venv/bin/python -m compileall -q src/context_manager
.venv/bin/python -m pytest tests -m 'not local_model' -q
.venv/bin/python -m pytest tests/test_f06_local_model.py -m local_model --local-model-config local/model.toml -q
git diff --check
```

测试标记 `local_model` 必须在 F01 注册，默认运行基础测试不会触发模型调用。F10 通过后按用户要求统一提交和合并，阶段中保留工作树与交接记录。初始文件未被 Git 跟踪时，提交准备阶段还需执行 `git diff --cached --check`，并将暂存内容与最后一次测试清单核对。

交付时复核远端是否仍为空。为空时完成一次初始提交并发布 `main`，把合并状态记为 `not_applicable_initial_publication`。已存在目标分支时，将最终候选与其基线对照并统一合并。合并产生代码变化时，重跑受影响检查。Git 操作及其权限按当时环境执行。

## 7. 首轮设计检查

本轮只检查设计材料的链接、功能依赖、状态记录与既有示例补丁的可应用性。所有产品功能测试初始值为 `not_run`，设计文档检查单独登记。
